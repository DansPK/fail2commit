## Remaining finding

**Medium, VM-R4-01 — the feature-query deadline does not bound synchronous pipe inspection.** `windows/ffi.rs:1161-1172` creates anonymous pipes with `CreatePipe`; it does not request overlapped I/O. `CappedPipeReader::drain_chunk` calls `PeekNamedPipe` and then a synchronous `File::read` on the control thread (`vm/windows.rs:682-733`). Both calls occur after a deadline check, but the next deadline check cannot run while either call is blocked. [Microsoft's `PeekNamedPipe` reference](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-peeknamedpipe) explicitly says the function can block on a synchronous handle in a multithreaded application. [Microsoft's anonymous-pipe documentation](https://learn.microsoft.com/en-us/windows/win32/ipc/anonymous-pipe-operations) says anonymous pipes do not support overlapped `ReadFile` and describes blocking reads/writes. Trigger: a pipe operation stalls inside the single control loop while the query or descendant retains the writer; the loop cannot enforce `CONTROL_GRACE` or call cleanup until that operation returns. The reported finite-output and continuous-descendant tests exercise normal polling, not a blocked pipe operation. **Fix:** use a pipe/IO design with a documented cancellation or finite-wait completion mechanism, or otherwise establish a supported bound for these exact synchronous operations; inject a stalled pipe operation and verify timeout, job termination, and uncertainty reporting. The new design is a substantial improvement over unbounded reader joins, but should not be described as a proven whole-query deadline yet.

The pre-resume test sleeps 250 ms inside the production spawn helper and checks that the fixture's `query.started` file is absent during the delay, then present after resume (`vm/windows.rs:1048-1068`). It exercises the real creation path rather than merely testing a predicate. The continuous-output test injects a failed `terminate` callback and asserts an error before three seconds (`:1070-1082`); it does not independently check descendant exit or the injected result against a real Win32 termination failure. In production, the callback is `tree.terminate` (`:747-761`), and a failure also triggers root termination (`:846-866`); `KILL_ON_JOB_CLOSE` applies when the tree handle drops. These paths still need Windows fault and process-exit evidence.
