## Findings

1. **High — Findings/error completion waits on the window.** `crates/fail2commit/src/cmd/progress_ui.rs:159-168`, `:260-281`. On any guarded npm or pip review ending with findings or an error, `finish()` sends `Finish` and then joins the GUI thread. That thread deliberately keeps the window open until the user clicks Close. Thus `npm::execute` / `pip::install` cannot return to the CLI response and exit until the click, and unattended callers wait indefinitely even though the review has ended. Trigger: approve a finding in an interactive Windows install, leave the result window open, and observe that the CLI result/exit is withheld. Keep result-window lifetime independent of the install command; deliver the final result without joining the GUI thread on the review path (and use a lifetime mechanism that can keep the window visible after CLI completion). Closing a window during an active review must not signal pipeline cancellation.

2. **Medium — pip reports downloads complete only after the actual download.** `crates/fail2commit-core/src/pip/mod.rs:241-284`. The pip `--dry-run` call uses the local proxy to fetch the wheels during resolution; `DownloadVerify` starts only after the dry run and report parsing, then immediately advances to `wheels.len()`. Trigger: a slow wheel download in `pip install <pkg>`; the UI remains at `Resolve (0/1)` during network transfer, then jumps to `DownloadVerify (N/N)` without showing the package being downloaded. Emit the download/verification phase and package completion events from the proxy or staging path as each verified wheel finishes, using the final plan total once known (or 0 while unknown per the frozen contract).

3. **Medium — npm's download count is an index, not completed packages.** `crates/fail2commit-core/src/npm/review.rs:137-154`, `crates/fail2commit-core/src/npm/mod.rs:309-313`. Up to eight workers fetch unique artifacts concurrently; each reports `(n + 1)` after its own fetch. A fast higher-index fetch can make `done` show `total` while a lower-index artifact is still downloading. The count also advances after a failed fetch. Trigger: two or more packages with one slow first artifact and fast later artifacts; the displayed completion count outruns actual verified packages. Increment a shared successful-completion counter after each verified fetch, and reconcile the count with the phase total (which is currently all plan entries, including duplicate artifacts).

4. **Medium — npm marks script-output scanning complete before it runs.** `crates/fail2commit-core/src/npm/mod.rs:598-613`. `Step::ScanOutput` is immediately followed by `advance(output.len(), "")`, before `review_output(...)` performs the scan. Trigger: a lifecycle script produces enough files for a noticeable output review; the window displays `ScanOutput (N/N)` throughout the pending scan. Move the advancement after each completed output unit, or at minimum after `review_output` returns; remove the pre-scan completion event.

5. **Medium — npm code-scan findings are absent from the live count.** `crates/fail2commit-core/src/npm/mod.rs:354-384`. The YARA loop appends findings to `extra` and advances package progress, but never calls `progress.finding` for the newly found items. They appear only when the enclosing `execute` returns and replays outcome findings. Trigger: a YARA finding in an early package followed by a long scan or advisory lookup; the live UI still says `0 finding(s)`. Report each new YARA finding as the package finishes, preserving the sink's deduplication on final replay.
