## New finding

1. **Medium — pip moves to an earlier step after candidate downloads.** `crates/fail2commit-core/src/pip/proxy.rs:174-181,289-295`, `crates/fail2commit-core/src/pip/mod.rs:273-294`, `crates/fail2commit-core/src/progress.rs:8-19`. The first candidate fetch calls `step(DownloadVerify, 0)` while pip is still resolving. After the final report is parsed, `install_inner` calls `step(Resolve, 1)` and `advance(1, "dependency plan resolved")`, then calls `step(DownloadVerify, wheels.len())` again. A pip install that fetches any wheel during resolution therefore visibly goes `Resolve → DownloadVerify → Resolve → DownloadVerify`. The frozen contract says a flow may skip a step but **never goes back to an earlier one**; the backtracking fixture currently asserts this backward reset at `pip_install.rs:177-182`. Keep candidate fetch text and `0/0` activity within the Resolve phase, then enter DownloadVerify once the plan is fixed; alternatively obtain explicit approval to revise the frozen ordering contract and its consumers. Add an order assertion to the integration test so a regression cannot be normalized by the fixture.
