## New concrete regression

### LG-01 — High preactivation: Windows status reports hardened mode available while backend refuses it

The `39334cc` status glue sets Windows `probe_available = service && peer_auth && effect_probe` (`hardened/mod.rs:68-87`). `fail2commit hardened status` treats that bit as the complete acceptance gate and returns success with “hardened mode available” (`crates/fail2commit/src/cmd/hardened.rs:42-61`). The actual Windows backend still hardcodes `available = false`, `launcher_watchdog = false` and `platform_controls = false` (`hardened/mod.rs:450-505`), reflecting unfinished runtime controls and the unaccepted external FirewallAPI writer race. Trigger: an installed service authenticates and its fixed traffic-effect PROBE passes; the status command then claims full hardened availability despite the backend's refusal. This is a readiness/assurance error, not proof that normal jobs bypass their gate. **Fix:** make Windows status use the same complete backend gate, or keep its `probe_available` false until launcher, platform, traffic and external-writer requirements are accepted; expose `effect_probe_passed` only as a diagnostic field. Add a cross-platform status/backend consistency test. No old Windows code was re-audited.
