## 1. Scope and method

I read the backend end to end: `sandbox/mod.rs` (`run_job`), `isolation.rs` (the frozen contract),
`sandbox/windows.rs` (`probe`, `run_unprobed`, path/ACL/environment/output handling) and
`sandbox/windows/ffi.rs` (every Win32 call), plus the pinned dependency sources (`sandboxrs-windows-0.1.1`,
`rappct-0.13.3`) that `docs/sandbox-windows.md` makes claims about.

Each of the eleven mandatory controls listed in the review brief was checked against the code rather than the
documentation. Where a control was testable I wrote an adversarial test, ran it on this host, and kept it only
when it failed for the intended reason. Every finding below is tied to a line range. Two exploratory tests
failed first for reasons in my own test code (parallel `TMP`/`TEMP` mutation, `mklink` argument quoting); both
were fixed and the initial failures are recorded in §6 rather than dropped.

Nothing here changed an ACL on a real user directory, added a loopback exemption, or touched a production
repository. All staged paths were disposable temp directories and all commands ran with `-j 2`.

## 3. Findings

### S7B-001 — A hard link in the staged tree escapes the link/reparse rejection and moves an ACL grant outside the stage

- **Severity:** Medium · **Status:** CONFIRMED (reproduced) ·
  **Reproduction:** `tests/review_t007b_paths.rs::hard_link_inside_staged_tree_grants_access_to_a_file_outside_the_stage`
- **Locations:** `windows.rs:378` (the stage is walked for reparse points exactly once),
  `windows.rs:425-447` (`reject_reparse_tree` tests only `FILE_ATTRIBUTE_REPARSE_POINT`),
  `windows.rs:462-466` (`grant_tree` re-walks and grants by path without re-checking attributes),
  `ffi.rs:224-296` (`grant` → `SetNamedSecurityInfoW`)

**Failure scenario.** `reject_reparse_tree` is the only link defence and a hard link (`fs::hard_link` /
`CreateHardLinkW`, no privilege needed) is not a reparse point, so it passes. `grant_tree` then calls
`ffi::grant` on the *path*, and `SetNamedSecurityInfoW` rewrites the DACL of the **file object**, which the
link shares with a target outside the stage. The reproduction stages
`<stage>\read-only\linked-input.txt` as a hard link to `<other temp dir>\outside-secret.txt`; the grant gives
the package SID read/execute on that path, the child reads the link inside its granted tree, and the artifact
is `native-work: OUTSIDE-SECRET`. So: (a) an ACE is written to an object outside the declared roots, which is
exactly what "staged-only grants" promises never happens; (b) content the stager merely *linked* becomes
readable inside the sandbox, defeating the purpose of the reparse check; (c) `revoke` removes the ACE again,
so the mutation is silent. The same walk leaves a TOCTOU gap: the attribute check happens at `378`, while
`grant_tree` re-opens every path by name at `465-466`.

**Suggested fix.** Reject staged files whose link count is not 1 (`GetFileInformationByHandle` →
`nNumberOfLinks`) and grant through a handle opened with `FILE_FLAG_OPEN_REPARSE_POINT |
FILE_FLAG_BACKUP_SEMANTICS`, verifying volume serial + file index against the validated entry. Alternatively
have the stager prove copy semantics (compare file IDs against the source tree) before granting.

### S7B-002 — The loopback-exemption control is verified by executing an environment-selected binary and fails open

- **Severity:** Medium · **Status:** CONFIRMED (reproduced) ·
  **Reproduction:** `tests/review_t007b_systemroot.rs::probe_runs_an_environment_selected_binary_to_verify_the_loopback_control`
- **Locations:** `windows.rs:498-525` (`verify_no_loopback_exemption` builds and runs
  `<SystemRoot>\System32\CheckNetIsolation.exe`), `windows.rs:527-532` (`required_system_root()` reads
  `SystemRoot` from the environment and only requires it to be absolute), `windows.rs:109-114` (the probe also
  stages `<SystemRoot>\System32\cmd.exe` as the "trusted probe executable"), `windows.rs:157-167` (seven
  controls are marked verified after that one run)

**Failure scenario.** `%SystemRoot%` is process environment, so a caller-controlled environment supplies both
the verifier and the verdict: a `System32\CheckNetIsolation.exe` that prints nothing and exits 0 satisfies
`windows.rs:515-523`, because the fresh random package SID cannot appear in empty output. Reproduced with
`%SystemRoot%` pointing at a disposable temp tree containing a real `cmd.exe` copy plus a stand-in that writes
a marker file — `probe()` executed the stand-in **unsandboxed in the trusted parent** and returned

```text
probe available=true detail=all mandatory AppContainer controls verified; LPAC is not enabled or claimed
controls=[("appcontainer-zero-capabilities", true), ("no-loopback-exemption", true), ... all true]
```

A mandatory network control can be reported verified without being verified, and the `available=true` gate that
permits package code to run is decided by an executable the caller chose. The same unvalidated `SystemRoot`
is emitted into the child environment at `windows.rs:545-546`.

**Suggested fix.** Do not derive the verifier path from the environment: use `GetSystemDirectoryW` /
`GetSystemWindowsDirectoryW` and refuse to continue when `%SystemRoot%` disagrees with it. Better, drop the
external verifier: query the container network configuration (`NetworkIsolationGetAppContainerConfig`) or
attempt a connection from inside the freshly created probe container, neither of which an environment
variable can influence.

### S7B-003 — The "staged temp directory" anchor is caller-controlled and degrades to the real user profile

- **Severity:** Medium · **Status:** CONFIRMED (reproduced) ·
  **Reproduction:** `tests/review_t007b_tempdir.rs::temp_dir_anchor_is_caller_controlled`
- **Locations:** `windows.rs:338` (`canonical_dir(&std::env::temp_dir(), "system temp directory")`),
  `windows.rs:370-377` (every granted root must live under one first-level child of that anchor),
  `windows.rs:221-225` (grants then apply recursively to those roots)

**Failure scenario.** `std::env::temp_dir()` is not a system fact: it is `%TMP%`, then `%TEMP%`, then
`%USERPROFILE%`. Reproduced on this host: with `TMP`/`TEMP` pointed at a disposable directory it returns that
directory, and with `TMP`/`TEMP` removed it returns **`C:\Users\<user>\`**, the real user profile. Driving the
product code with `TMP`/`TEMP` aimed at a directory fail2commit never created, `ValidatedPaths::new` accepted
`<that root>\job\work` and the run continued as far as `CreateProcessW`, i.e. the containment check passed.
With `TMP`/`TEMP` unset the anchor *is* the user profile, so a `work_dir` of `%USERPROFILE%\<anything>`
receives recursive `FILE_MODIFY` (`windows.rs:225`, `windows.rs:462-487`) and its `read-only` sibling receives
recursive `FILE_GENERIC_READ|FILE_GENERIC_EXECUTE`, with `revoke` and `reject_reparse_tree` walking real
profile content. `docs/sandbox-windows.md:26` ("No real checkout, home, or user directory is granted") does not
hold in an environment without `TMP`/`TEMP`, and it is the stager — not this backend — that decides where
`work_dir` points.

**Suggested fix.** Anchor on the OS-provided temp path (`GetTempPath2W` or
`SHGetKnownFolderPath(FOLDERID_LocalTemp)`), ignore `%TMP%`/`%TEMP%`, and refuse an anchor that equals or
contains `USERPROFILE`, `LOCALAPPDATA`, `APPDATA` or any known shell folder. Better, record the staging root
when fail2commit creates it (a marker inside the stage, or a `JobSpec` field) and require granted roots to live
under that recorded root instead of a re-derived one.

### S7B-004 — `run()` can block forever: terminate results are discarded and no post-run wait has a deadline

- **Severity:** Medium-Low · **Status:** CONFIRMED (exact code path; hang not reproduced)
- **Locations:** `windows.rs:293-297` and `windows.rs:299-301` (`job_object.terminate();` result discarded),
  `windows.rs:315` (`wait_empty`), `windows.rs:317-318` (`join_drain` without a timeout), `ffi.rs:560-563`
  (`terminate` returns `bool`), `ffi.rs:565-576` (`wait_empty` has no deadline and swallows query errors via
  `is_ok_and`), `ffi.rs:626-632` (`kill` ignores both return values)

**Failure scenario.** If `TerminateJobObject` fails, `wait_empty` spins at the `next_message(25)` rate forever:
`active_processes()` keeps returning an error, `is_ok_and` turns that into `false`, and `next_message` returns
`None` after each 25 ms wait. `join_drain` behaves the same if any inherited write-end handle outlives the job.
`run()` then never returns, so the configured timeout is not an upper bound and no error reaches the caller, the
UI or the policy layer. On the pre-assignment error paths (`windows.rs:254`, `259`, `267`) `Spawned::kill` also
ignores failures, so a suspended root process could survive (harmless while suspended, but leaked).

**Suggested fix.** Check the `TerminateJobObject` result and return `IsolationUnavailable` when it fails; bound
`wait_empty` and both drain joins by the job timeout plus a grace period and return an error instead of
spinning; make `kill` return a result.

### S7B-005 — The probe verdict is a cached snapshot and two "verified" controls are inferred, not measured

- **Severity:** Low · **Status:** CONFIRMED (exact code path)
- **Locations:** `windows.rs:37-40` (`OnceLock` caches the first probe for the whole process),
  `windows.rs:117-128` (the probe authors its own stand-in pipes and SDDL), `windows.rs:148-167` (all controls
  marked true after one launch), `windows.rs:203-327` (`run_unprobed` re-verifies profile, token, ACL read-back
  and job limits, but never the pipe or the handle list), `ffi.rs:851-892` (`listening_pipe`)

**Failure scenario.** `approval-ipc-denied` and `explicit-stdio-handle-list` are named mandatory controls, but
neither is measured. The approval-IPC check proves a child cannot open a pipe whose DACL the probe itself
wrote; the real approval pipe does not exist yet (`crates/fail2commit-core/src/ipc/mod.rs:11-13` returns
`None`), so nothing ties the control to the surface that will be protected. When T-009 adds
`\\.\pipe\fail2commit-approval-<SID>` with a DACL granting the current user, the cached probe would still
report `available=true` and the control as verified. The handle-list control is attributed from code
inspection: the probe would still pass if the handle list were dropped, because it only inspects the child's
exit code and pipe connections.

**Suggested fix.** Verify the approval-IPC control against the real pipe once T-009 defines it (open it from
inside a probe container and require `ERROR_ACCESS_DENIED`); verify handle containment empirically (spawn with
a known inheritable sentinel handle and require the child to fail reading it). Re-probe per operation, or
re-verify the environment-dependent controls inside `run()`.

### S7B-006 — ACL revocation failures are silently discarded

- **Severity:** Low · **Status:** CONFIRMED (exact code path)
- **Locations:** `windows.rs:490-496` (`impl Drop for StagingGrants` → `let _ = ffi::revoke(...)`),
  `ffi.rs:301-367` (`revoke` returns a `Result`)

**Failure scenario.** `revoke` reports every failure it can detect and `Drop` throws all of them away, so a
failed revoke leaves an explicit `ALLOW` ACE naming the job's package SID on a staged path with no signal, no
retry and no record. Exposure is limited because the profile and SID are deleted immediately afterwards and the
SID is a random 128-bit value that cannot be recreated, but "no leaked ACL entries" is unverified by
construction and the cleanup result should be observable for diagnostics.

**Suggested fix.** Collect failures in `drop` and expose `StagingGrants::release() -> Result<()>` that the happy
path calls explicitly, keeping `Drop` as a best-effort backstop.

### S7B-007 — `ffi::grant` does not handle a NULL input DACL

- **Severity:** Low · **Status:** PLAUSIBLE (requires a staged object with a NULL DACL)
- **Locations:** `ffi.rs:230-241` (`GetNamedSecurityInfoW` may return `psidDACL = NULL`; not checked),
  `ffi.rs:267` (`SetEntriesInAclW(1, &ea, dacl, &mut new_dacl)` with a possibly NULL `dacl`), `ffi.rs:388-393`
  (the *same* case **is** rejected in `allowed_mask`)

**Failure scenario.** A NULL DACL means "full access to everyone". Passing it as `pOldAcl` builds a new ACL from
the explicit entries only, so the write replaces full access with a package-only DACL: the owner's access is
dropped, the `allowed_mask` read-back then fails (`ffi.rs:388`), and the run aborts *after* the DACL was
rewritten, leaving the staged object package-only and the failure looking like a read error. The
inconsistency with `allowed_mask`, which does check, shows the case was considered and forgotten here.

**Suggested fix.** Reject `dacl.is_null()` in `grant` with `IsolationUnavailable` before writing anything.

### S7B-008 — `LOCALAPPDATA` is copied from the parent environment into the child

- **Severity:** Low · **Status:** CONFIRMED (exact code path)
- **Locations:** `windows.rs:547-553`, documented at `docs/sandbox-windows.md:32`

**Failure scenario.** `SystemRoot` and `SystemDrive` are genuinely needed by loader and shell; `LOCALAPPDATA`
is an application-profile path the child does not need (the AppContainer writes only to its own
`Packages\<profile>` folder). It is copied from the parent environment with no validation beyond "absolute", so
it leaks the user's profile path into untrusted package code and lets a caller steer the value. The docs
justify it with Win32 error 203, which is normally caused by a missing hidden `=C:` drive entry.

**Suggested fix.** Establish the minimum variable set empirically per Windows build and derive any genuinely
required value from the OS instead of the parent environment.

### S7B-009 — The pinned dependency enforces nothing; SPEC-007's "integrate or pin a narrow patch" is not met

- **Severity:** Low (process/compliance plus supply-chain surface) · **Status:** CONFIRMED (exact code path)
- **Locations:** `crates/fail2commit-core/Cargo.toml` (`sandboxrs-windows = "=0.1.1"`), `windows.rs:96-99`
  (`let _required_dependency_path = sandboxrs_windows::BackendPreference::AppContainer;`)

**Failure scenario.** The only use of the dependency is a `let` binding whose value is discarded; it exists to
keep the crate linked and make a future migration visible. Every control is reimplemented locally while
`sandboxrs-windows` and `rappct` (and their own `windows-sys` versions) stay in the build graph. SPEC-007 asks
for integration with the AppContainer path *or* a narrowly scoped upstream fix/pinned patch; a full local
reimplementation is neither, so the pin and the dependency review describe code that never runs. That review is
itself accurate — `compile.rs:33` grants `FILE_ALL_ACCESS` for read-write rules, `compile.rs:49-63` mutates
broad system directories best-effort, `job.rs:66-71` uses a per-process limit with no UI restrictions, and
`spawn.rs` has no read-back — but none of it is exercised.

**Suggested fix.** Either record an explicit change request amending SPEC-007 (local Win32 implementation
instead of dependency integration) and drop the unused dependency, or route the local code through the
dependency's types so the pin has meaning.

### S7B-010 — `disabled_and_unavailable_policy_never_launches_package_code` contains a vacuous assertion

- **Severity:** Low · **Status:** CONFIRMED (exact code path)
- **Locations:** `crates/fail2commit/tests/sandbox_windows_matrix.rs:88-105`

**Failure scenario.** The test creates `marker`, calls `script_decision` twice and asserts `!marker.exists()`.
Nothing ever hands `marker` to a backend, script or process, so the assertion cannot fail and the test only
proves the policy table. Its name and the verify row (`VERIFY-2026-11-08-sandbox-windows.md:71`, "Sandbox
disabled | Pass … launch marker is absent") imply a launch was attempted and prevented.

**Suggested fix.** Stage a helper whose first action is to create that marker, drive the decision-gated entry
point, and assert both that the marker is absent and that no `JobSpec` reaches the backend (a counting mock is
enough).

### S7B-011 — The Git control is never asserted, but the verify report marks it "Pass"

- **Severity:** Low · **Status:** CONFIRMED (exact code path)
- **Locations:** `tests/fixtures/sandbox-windows/attacker.rs:58-60`
  (`let _ = Command::new(git).arg("--version").status();`), `sandbox_windows_matrix.rs:129-136`,
  `VERIFY-2026-11-08-sandbox-windows.md:62`

**Failure scenario.** The hostile helper launches host `git.exe` and discards the result, so whether Git starts,
is denied, or reaches the network is not observable in the test outcome. The row "`git.exe` | Pass … if it
starts, it runs under the same verified zero-capability token" is an assumption, not evidence: a regression
that let Git execute with network access would not fail this test.

**Suggested fix.** Assert on the Git result (require the spawn to fail, or require `git ls-remote` against a
disposable local remote to fail) and record the observed error code; otherwise move the row to Pending.

### S7B-012 — The handle-inheritance test can pass for the wrong reason and leaks the parent's inherit flag

- **Severity:** Low · **Status:** PLAUSIBLE (depends on handle numbering)
- **Locations:** `sandbox_windows_matrix.rs:151-172` and `:259-272`, `attacker.rs:103-114`

**Failure scenario.** The child is told a numeric handle value and reports "denied" if `ReadFile` fails. If that
number happens to name a *different* handle in the child's table (for example a stdio pipe end), the read fails
for the wrong reason and the test still passes. The test also sets `HANDLE_FLAG_INHERIT` on the parent's file
handle and never clears it, so it stays inheritable for the rest of the process and would be inherited by any
later child created without a handle list.

**Suggested fix.** Pass a synthetic passphrase through the sentinel handle and require `ReadFile` to fail with
`ERROR_INVALID_HANDLE`; clear `HANDLE_FLAG_INHERIT` when the test finishes; assert on the reported error code
rather than a single boolean.

### S7B-013 — `probe()` is far from "cheap enough to call per operation"

- **Severity:** Low (NFR observation) · **Status:** PLAUSIBLE (observed cost, not measured rigorously)
- **Locations:** `isolation.rs:82-84` (contract wording), `windows.rs:101-201` (probe creates a profile, stages
  `cmd.exe`, runs three sandboxed launches and one unsandboxed `CheckNetIsolation` run)

**Failure scenario.** The first `probe()` in a process creates and deletes an AppContainer profile, copies
`cmd.exe`, writes ACLs, launches three processes and spawns `CheckNetIsolation.exe`. My probe-only test took
≈2.4 s and the matrix suite ≈12 s for five tests, most of it probe work. The result is cached per process, so a
single CLI invocation pays it once — acceptable today, but it contradicts the contract text and will be paid
again by every short-lived invocation (hooks, editor requests) that touches the backend.

**Suggested fix.** Either narrow the contract wording, or cache the verdict across processes with a verified
fingerprint (OS build, backend version) plus a cheap fast path.

## 4. Checked and sound

Verified against the code, and where marked by running it. These are not defects.

1. **No network capability and no untrusted capability list.** `SECURITY_CAPABILITIES` is built with
   `Capabilities = null, CapabilityCount = 0` (`ffi.rs:667-672`); no capability SID list is ever derived from
   `JobSpec`, arguments, settings or workspace data, and the only SDDL literal in the module is the probe's own
   pipe DACL (`windows.rs:120-121`). Neither `internetClient`, `internetClientServer` nor
   `privateNetworkClientServer` appears in any code path that runs. The suspended child's token is read back and
   the run aborts unless it is an AppContainer with the expected SID and `GroupCount == 0`
   (`windows.rs:251-263`, `ffi.rs:800-831`); an LPAC token is refused (`windows.rs:264-271`).
2. **No loopback exemption is ever added.** The only `CheckNetIsolation` call uses `LoopbackExempt -s`,
   read-only, with a cleared environment (`windows.rs:502-506`); `-a`/`-d` appear nowhere. S7B-002 is about the
   soundness of the verdict, not about adding an exemption.
3. **`..` cannot redirect a grant.** Every path is canonicalized before any comparison (`windows.rs:388-397`)
   and containment is component-wise `starts_with`. Explored: `work_dir = <stage>/work/../../../..` was refused
   during validation (`read_only and work_dir must not overlap`) — fail-closed, no ACL written.
4. **Junctions and directory symlinks are rejected.** Reproduced:
   `review_t007b_paths.rs::junction_inside_staged_tree_is_rejected` → `staged path is a reparse point`. The walk
   tests the attribute before recursing (`windows.rs:434-444`), so it does not follow the link either. Only hard
   links escape (S7B-001).
5. **Grant scope and masks are minimal and read back.** Read-only roots get
   `FILE_GENERIC_READ|FILE_GENERIC_EXECUTE`, the work root gets `FILE_MODIFY` (`windows.rs:222-225`).
   `FILE_MODIFY` (0x001301BF) deliberately excludes `WRITE_DAC` (0x00040000) and `WRITE_OWNER` (0x00080000), so
   the sandbox cannot rewrite a DACL or take ownership. Every grant is read back, and a single bit outside the
   requested mask aborts the run (`windows.rs:468-479`). Relative paths, non-directories, overlapping
   read-only/work roots, and a program outside the read-only roots are refused before the first ACL write
   (`windows.rs:347-377`).
6. **Handle inheritance is explicit.** `PROC_THREAD_ATTRIBUTE_HANDLE_LIST` carries exactly stdin/stdout/stderr
   (`ffi.rs:673`, `705-713`); the stdio pipe read ends are never inheritable (`ffi.rs:594-604`); the three
   handles are inheritable only inside a process-global mutex and are cleared immediately after `CreateProcessW`
   (`ffi.rs:728-761`). The product test that marks an unrelated handle inheritable and fails to read it from the
   child passes on this host.
7. **Job Object, verified before anything runs.** Kill-on-close, active-process limit, job-wide memory limit and
   die-on-unhandled-exception are set, all eight UI restriction classes are set, breakaway and silent-breakaway
   are absent, and every field is queried back from the kernel before launch (`ffi.rs:494-532`). The root is
   created suspended, token-verified, assigned, re-checked with `IsProcessInJob`, and only then resumed
   (`windows.rs:243-279`, `ffi.rs:535-550`) — no grandchild can run before assignment.
8. **Timeout terminates the job and the backend waits for the tree to empty.** `TerminateJobObject` applies to
   the whole job and the drain waits for `ActiveProcesses == 0` (`windows.rs:292-315`); reproduced by the matrix
   test (`TimedOut`). The missing deadline is S7B-004; the mechanism itself is correct.
9. **Output draining is bounded and deadlock-free.** One mutex-protected budget is shared by two concurrent
   drains; bytes past the cap are still read and dropped so the child never blocks on a full pipe, and
   `truncated` is set on the first dropped byte (`windows.rs:661-695`). Reproduced at 31 bytes in the matrix and
   127 bytes inside the probe.
10. **The environment is built, not inherited.** The block comes from `job.env` only; keys are validated (no
    NUL, no `=`) and deduplicated case-insensitively; `PATH` is absent unless the job asks for it
    (`windows.rs:534-609`). The matrix test asserts `PATH` unset and the allowlisted value present.
    (`LOCALAPPDATA` is the exception: S7B-008.)
11. **Every pre-launch failure fails closed.** All setup paths return `IsolationUnavailable`; a missing or zero
    process/memory limit or a zero timeout is refused (`windows.rs:205-217`); a token that is not the fresh
    zero-capability container aborts the run (`windows.rs:258-271`); `run()` refuses to launch when `probe()` is
    unavailable (`windows.rs:42-51`). `missing_mandatory_limit_fails_before_launch` proves the no-launch
    property with a marker file.
12. **`unsafe` is narrow and commented.** `#![deny(unsafe_code)]` is crate-wide (`lib.rs:15`); `windows.rs`
    contains no `unsafe`, and `ffi.rs` opts in 26 times, once per function, each with a SAFETY note.
    `GetLastError` is read immediately after `CreateProcessW` (`ffi.rs:756-757`), both `LocalAlloc` blobs are
    freed exactly once (`ffi.rs:287-288`, `358-359`, `424`), the attribute-list buffer is `usize`-aligned and
    outlives the list (`ffi.rs:677-693`), and token/ACL buffers are `usize`-aligned with API-reported sizes
    (`ffi.rs:775-788`). `cargo clippy --all-targets -- -D warnings` is clean for the package, including my tests.
13. **Output is treated as untrusted.** The backend returns raw bytes and never parses, interprets, logs or
    re-encodes them.

## 8. Limitations of this review

- **S7B-004 (hang) was not reproduced.** The defect is a missing deadline plus a discarded `TerminateJobObject`
  result; forcing `TerminateJobObject` to fail on a live job was out of proportion for a read-only review.
- **S7B-007 (NULL DACL) was not reproduced.** It would require deliberately loosening an ACL, which the review
  rules forbid outside disposable temp trees; it stays PLAUSIBLE on the code path.
- The live external endpoint test (`1.1.1.1:443`) was not run: no authorization for live network traffic.
- The full staged MinGW GCC build was not attempted; the original verify report's blocker (a legitimate closure
  needs ~11.9 k files / 961 MB) still stands and this review cannot settle it.
- Linux/T-007a (`sandbox/linux.rs`, the export step) is outside this assignment and was not reviewed. Note for
  the coordinator: `sandbox/mod.rs:45-48` still returns `not_implemented("sandbox export")`, so `run_job`
  cannot export artifacts today on either platform.
- `quote_windows_arg` (`windows.rs:627-659`), `environment_block` and `token_info` were reviewed by reading them
  against the documented MSVCRT / `GetTokenInformation` rules; no fuzzing or differential test was run. Argument
  quoting and the synthesised `=C:` entries would benefit from property tests before release.
- ACL state after an aborted run was not audited with an independent DACL dump; I relied on the product's own
  read-back plus the reproduction outcomes.

## 9. Response to the shipped verify report

`docs/dev/verify/VERIFY-2026-11-08-sandbox-windows.md` is honest about pending evidence and accurate about what the
code does; the offline matrix does pass on this host. Two rows overstate what was measured: **"`git.exe` |
Pass"** rests on a discarded return value (S7B-011) and **"Sandbox disabled | Pass … launch marker is absent"**
rests on an assertion that cannot fail (S7B-010). The row **"Restrictive staged ACLs | Pass"** is correct for the
tests that were run but does not cover hard links (S7B-001) or an environment without `TMP`/`TEMP` (S7B-003),
which is why `docs/sandbox-windows.md:26` ("No real checkout, home, or user directory is granted") should be
qualified.

## 10. Verdict

**Not certified.** The AppContainer backend implements every mandatory control in the right shape, and most of
them hold up under adversarial reading and testing. Three controls, however, report success while being bypassable
under the stated preconditions (S7B-001, S7B-002, S7B-003), and each is reproduced on this host with a committed
test. I recommend change requests for S7B-001 and S7B-002 (both are narrow, local fixes) and treating S7B-003 as a
precondition on the stager's contract before FR-007 can be called verified.
