## HT-R3-01 disposition

**Source-fixed for refusal across service restart, not yet recovered.** `ActiveLaunchGuard::create` writes and syncs a protected marker before `CreateProcessAsUserW` (`service.rs:548-787,1847-1879`), and a suspended process has its PID and creation time persisted before `ResumeThread` (`:1887-1963`). Startup checks the marker before stale snapshot sweep; present *or invalid/unreadable* state sets the service's fail-closed latch (`:1060-1088`). STATUS and LAUNCH reject while latched (`:1165-1190`). The PID/creation pair is recorded to avoid future PID-only recovery, but the current code **does not use it to reconcile a process**: a marker left by a crash remains a permanent refusal until separately repaired. That is safe as a source-level default; restart cleanup and recovery are still pending SPEC-018 behavior.

## Findings

### PL-01 — Medium: uninstall bypasses active-launch marker when the SCM service is absent

The marker check in `lifecycle.rs:1398-1419` is inside the `OpenServiceW` success branch. When SCM returns `ERROR_SERVICE_DOES_NOT_EXIST`, control skips directly from `:1322-1332` to right removal and `NetUserDel` (`:1433-1459`) without checking the marker. Trigger: an interrupted/unconfirmed launch leaves `active-launch.json`, and the service is subsequently absent from SCM (a partial uninstall or external service deletion). The account and rights can be removed before the nonempty protected state directory makes the final directory removal fail; the command can therefore partially tear down resources with containment unresolved. **Fix:** check and validate the active marker before any SCM/account/right/binary mutation, including the missing-service branch, and retain all owned resources until recovery proves the launch tree ended. VM fault injection should cover service deletion with a marker present.

### PL-02 — Medium, pre-activation: marker clears before kill-on-close job ends descendants

`run_snapshot_as_sandbox` creates a kill-on-close job and adds it to the launcher process attributes (`service.rs:1677-1763`), but holds `_job_handle` until function return. After the launcher process is signaled, it unloads the user profile and clears `active-launch.json` (`:2025-2065`) **before** that job handle drops. A launcher can have descendants still in the job after its own handle is signaled; the marker is absent while the profile is unloaded and the descendants have not yet been killed by closing the job. Trigger: launcher exits while a child remains in its containment job, including a future phase-2 child. A service crash/restart in this interval permits startup sweep and later LAUNCH without proof of tree termination. **Fix:** close/terminate the job and establish a bounded process-tree completion barrier before profile unload and marker removal; if completion is unconfirmed, retain the marker. Verify a launcher with a lingering child in a Windows VM. At this revision the launcher refuses package code, so this is a pre-activation ordering defect.

### PL-03 — Medium, pre-activation: unconfirmed launch snapshot is dropped despite retained marker

`launch_windows_request` owns a `TempDir` snapshot (`service.rs:2172-2175`). If `run_snapshot_as_sandbox` returns an unconfirmed-containment error, the `?` drops that `TempDir` even though the persistent marker is retained (`:2033-2046`). The destructor can remove snapshot files while the launcher may still be alive, and the marker's `snapshot_dir` then refers to a missing or partly removed path. This defeats the stated rule that marker presence blocks snapshot sweeps until reconciliation; only the *startup* sweep is gated. **Fix:** on an unconfirmed result, deliberately retain the snapshot directory and its ownership record for later recovery; clean it only after tree termination is established. A Windows VM test should inject unconfirmed termination and inspect the snapshot and marker before restart.

## Boundary observations and exact checks

- Marker parsing bounds JSON and requires a paired nonzero PID/creation time (`service.rs:548-606`); `active_launch_pending` opens with reparse protection and validates SYSTEM owner (`:623-662`). A malformed marker blocks startup sweep rather than being treated as absent. These are source-level checks; the marker DACL, crash windows and PID-creation identity need VM validation. The stored `snapshot_dir` currently points to `jobfile.parent()` (the `input` subdirectory), not the top-level job directory (`:1847-1850`), so future reconciliation must define and validate that field before using it for deletion.
