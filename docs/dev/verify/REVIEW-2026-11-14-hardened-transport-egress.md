## New findings

### TE-01 — High: a response can be discarded before the authenticated client reads it

The listener calls `write_pipe_response` and immediately `DisconnectNamedPipe` (`service.rs:1878-1889`), including error replies at `:1813-1831`. The client reads only *after* writing its request (`:188-200`). A scheduler handoff after the server's `WriteFile` but before the client's `read_until` lets the disconnect discard unread reply bytes; the caller observes an incomplete/broken response despite a completed STATUS or LAUNCH. Microsoft explicitly documents that [DisconnectNamedPipe discards unread pipe data](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-disconnectnamedpipe). For LAUNCH, the operation can finish while the caller loses its result, making retries and grant cleanup depend on marker state. **Fix:** add a bounded client acknowledgement or another completion protocol before disconnecting; prove response delivery and timeout behavior with installed-service STATUS/LAUNCH/reconnect tests. A plain `FlushFileBuffers` would wait indefinitely for a silent peer unless bounded separately.

### TE-02 — Medium: nonblocking `ConnectNamedPipe` is treated as a client connection

The instance is created with `PIPE_NOWAIT` (`service.rs:1740-1748`, numeric `0x00000001`). The loop treats any nonzero `ConnectNamedPipe` return as connected (`:1763-1778`), immediately configures the pipe and asks for a client PID (`:1793-1809`). In nonblocking mode, the *first* connect call on a disconnected instance can return nonzero merely to make the instance available, with no client yet; Microsoft states that a good connection exists only after `ERROR_PIPE_CONNECTED` ([ConnectNamedPipe remarks](https://learn.microsoft.com/en-us/windows/win32/api/namedpipeapi/nf-namedpipeapi-connectnamedpipe)). A quiet service can therefore cycle through failed PID lookups/disconnects without the intended 50 ms wait, consuming CPU and narrowing client connection windows. **Fix:** model LISTENING/CONNECTED/NO_DATA explicitly; do not authenticate or disconnect on the initial nonzero availability transition, and back off on recoverable no-client states. Verify idle CPU and repeated authenticated reconnects in the installed Win10 service.

### TE-03 — Medium: package ACL failure loses the persistent launch refusal before cleanup completes

After the process-tree barrier, the service unloads the account profile and clears `active-launch.json` (`service.rs:3001-3023`), then attempts `package_grants.release()` (`:3028-3036`). If revocation fails, it sets only the process-local latch and returns. The crash-safe revoke journal may remain (`windows.rs:1715-1727,1752-1819`), but service restart sees no marker and accepts STATUS/LAUNCH (`service.rs:1722-1729,1833-1858`); the client-side journal sweep at `:90-92` can be bypassed by a directly authenticated service request, and uninstall's marker gate sees no active marker. Trigger: failed ACL revocation followed by service restart or uninstall. **Fix:** retain the marker until grant revocation and WFP guard closure complete; on cleanup failure, leave a protected persistent refusal and require verified retry/recovery before accepting work or uninstall. Test injected revoke failure, restart, direct authenticated LAUNCH, and uninstall.

## Scoped boundary checks

- The private preparation request binds launch ID, PID, process creation time, derived package SID/profile and `NetworkMode::None` (`service.rs:1109-1133`); the launcher writes one bounded request and checks the acknowledgement before resuming its suspended child (`:1285-1342`; `windows.rs:675-755`). The service holds package grants and its dynamic WFP session until tree teardown (`service.rs:2832-2907,2968-3037`). These are source checks, not installed-service proof. The byte-pipe readers at `service.rs:989-1049,1356-1426` reject a frame if its length prefix is available before the remainder; a fragmented delivery may fail closed. Exercise this in the VM handshake test before relying on it as a runtime control.
- WFP installs and reads back six package-SID block filters across IPv4/IPv6 connect, resource assignment and receive/accept (`windows_wfp.rs:18-145`), with a dynamic session dropped after cleanup. The LPAC path checks the suspended child token before preparation and resume (`windows.rs:616-755`). Actual filter precedence/effect, process attributes, handle inheritance, diagnostic restoration, and grant revocation require privileged VM probes. The diagnostic path is guarded by both feature and debug assertions (`service.rs:3249-3262,3605-3627`; `protocol.rs:254-260`), and its child is killed before resume (`windows.rs:707-751`); no production package bypass was found in these changed paths.
- The Linux proxy now imports shared `Watch`, request parsing, destination classification and bait inspection (`linux/proxy.rs:8-20,167-219`; `egress.rs:11-126`). Most moved logic is equivalent. One narrow behavior change exists: old `content_length` returned `None` on the *first malformed* Content-Length; `egress.rs:119-125` skips it and may accept a later valid duplicate. This deserves a duplicate-header regression, but does not establish a new destination-policy bypass. Internet/proxy/loopback remain disabled for hardened Windows (`windows.rs:495-498`; `service.rs:3629-3634`).
