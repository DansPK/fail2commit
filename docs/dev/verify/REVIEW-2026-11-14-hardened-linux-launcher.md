# FR-027 Linux hardened launcher review (2026-11-14)

**Pinned implementation:** `4bf0004e1712781637e4a2c6556989d897b8a6f7` (parent `bae928333792e7dd8e5652b96408bc5f6adf3547`), one Linux launcher commit. **Verdict:** authenticated transport, root-owned snapshot, dedicated account/system scope, watchdog and ACL recovery paths are present, but the delta has one privilege-boundary defect and two recovery/containment defects. Root-installed controls and Internet egress remain unverified; this is not full FR-027 acceptance.

## Findings

### HL-01 — High: a caller-selected root-owned read-only tree receives sandbox ACLs

`linux_acl.rs:327-334` takes each `JobSpec.read_only` path directly from the authenticated installer's request. `canonical_job_dir(..., false)` accepts **either** peer-owned or root-owned directories (`:373-395`); `collect_tree` adds descendant files (`:398-445`); `open_acl_target` likewise accepts root-owned files (`:471-493`); and `GrantGuard::apply` grants the dedicated sandbox UID read/execute access with root-run `setfacl` (`:74-121,144-155,496-541`). The service calls this before launching the job (`service.rs:1315-1325,1363-1371`). The ordinary bind policy excludes `/etc`, `/root` and several ancestors, but allows a root-owned subtree beneath an otherwise permitted path such as `/home` (`linux.rs:81-86,398-422,642-645`); the service unit declares `/home` writable (`packaging/linux/fail2commit-hardened.service:21`). Trigger: a symlink-free, root-owned directory beneath an effectively writable permitted tree contains a file the installer cannot read; the installer submits it as `read_only` and runs a system tool to return its contents. The root service grants the sandbox UID access that the installer did not possess, and the job output crosses back to the installer. `ProtectSystem=strict` reduces which roots can be modified, but does not establish caller authorization for every accepted root-owned tree. **Fix:** require caller-owned staged `read_only` roots and descendants, or prove the authenticated peer already has the requested read/traverse rights before granting any sandbox ACL; keep service-owned snapshot paths in the separate fixed `extra` list. Test a peer-inaccessible root-owned fixture inside an allowed writable root and assert no ACL change or launch.

### HL-02 — Medium: journal write failure leaves an untracked partial recovery record

`linux_acl.rs:124-143` calls `write_journal(...)?` before constructing `GrantGuard`. `write_journal` creates the final `grant-*.json` path, then writes and syncs it without removing the path if write, file sync, or parent sync fails (`:724-746`). Trigger: a short write, I/O error or sync failure after `create_new`; the guard does not exist, so no caller owns the path for cleanup. On service start or the next request, `recover` scans the file and rejects zero/partial or malformed content (`:185-215`), leaving the install fail closed indefinitely until manual repair. **Fix:** on every post-create error, close and remove the exact file with checked result; if removal fails, return its durable path and retain a clear refusal state. Inject write/file-sync/parent-sync errors and verify restart recovery and retry behavior.

### HL-03 — Medium: watchdog-probe timeout/error does not confirm scope death

If the READY deadline fails, `linux_watchdog_probe` drops the watchdog and ignores `terminate_linux_scope` failure, then kills/waits only for the `systemd-run` wrapper (`service.rs:1136-1147`). Its later deadline branch does the same (`:1164-1171`). Neither branch calls `linux_scope_inactive` before returning; the scope has no ACL journal or durable active marker, while a later successful probe can set `probe_available=true` (`:1197-1219,1002-1010`). Trigger: systemd scope kill fails or times out after the probe payload starts. The service cannot establish that its sandbox process tree stopped, yet later readiness can pass while that scope remains. **Fix:** require a bounded inactive/readback barrier on every probe exit; retain a service refusal marker/latch if containment is unconfirmed and reconcile the exact scope identity at restart. Inject scope-kill and inactive-readback failures in a disposable root-installed guest.

## Source disposition and evidence limits

The client checks a root `SO_PEERCRED` server peer (`service.rs:343-386`); the server reads kernel `SO_PEERCRED` and accepts only the recorded non-root installer UID, excluding the sandbox UID (`:667-669,920-937,986-1020`). The service takes a bounded, metadata-stable peer-owned job file through an `openat` handle, writes a root-owned private snapshot, and passes only that path to the unprivileged launcher (`:1244-1355,1400-1415`). The launcher enforces root-owned/private snapshot ancestors, a regular bounded root-owned file and a required watchdog descriptor (`:229-288,291-340`); the service uses `systemd-run --scope --wait --pipe` with `setpriv --reuid/--regid/--init-groups`, bounded cgroup properties, and an inactive-scope check before normal ACL release (`:1372-1468`). `GrantGuard::release` gates ACL restoration on scope inactivity and recovery validates journal/target dev, inode and owner (`linux_acl.rs:158-230,234-309,765-789`). These are source-path dispositions, not installed-effect proof.
