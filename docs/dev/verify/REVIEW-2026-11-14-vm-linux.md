## Findings

1. **High, LV-01 — mandatory input mounts have no mount points.** `ValidatedPaths::new` requires at least one read-only staged root (`vm/linux.rs:621-624`), and the host assigns `f2cin0` for it (`:238-244`). The generated init creates only `$R/jobs/$id/work`, control and results (`vm/prepare.rs:891-898`); it then tries to mount `$R/jobs/$id/input-{index}` without creating those directories and discards mount errors (`:899-903`). The guest's resolved-input check requires those paths to exist (`vm_guest.rs:299-308`). Trigger: any normal VM job with its required input share. The input mount fails, guest dispatch cannot validate the path, no valid outcome is written, and the host reports unavailable after QEMU exits. **Fix:** create each configured input mount point before mounting, distinguish absent unused slots from a failed mount of a supplied slot, and fail init before launch on a required mount failure. Boot-test a one-input job and a missing input device.

2. **High, LV-02 — KVM guest dispatch checks a Xen sysfs interface.** `verify_linux_vm_context` requires `/sys/hypervisor/type` to exist and contain `kvm` (`vm_guest.rs:243-270`). The [Linux kernel's stable sysfs ABI](https://docs.kernel.org/admin-guide/abi-stable.html) documents that path under `sysfs-hypervisor-xen`, with value `xen` when running under Xen; it does not document a `kvm` value there. Trigger: an otherwise valid QEMU/KVM guest lacking that file. The guest refuses before reading the control request, so no job runs or outcome is published. **Fix:** use a supported KVM guest signal and, for the intended security boundary, bind dispatch to a trusted prepared-guest capability rather than treating a readable kernel command-line job ID as authentication. Test inside actual KVM and outside the guest with a syntactically valid control tree. The fresh ID ties request/outcome correlation but is not a secret.

3. **High, LV-03 — QEMU is spawned before timeout overflow validation.** `vm/linux.rs:280-290` starts QEMU, then applies `job.limits.timeout.checked_add(BOOT_GRACE)?`. A representability failure returns without killing or waiting for the new VM process and drops the stage/control/result guards. Trigger: a configured `u64` timeout whose `Duration` plus 45 seconds overflows. **Fix:** compute a checked absolute deadline before spawn; on every post-spawn error, kill and confirm QEMU exit before releasing mapped state. Test overflow with a spawn sentinel. This is the same ordering class as original Windows VW-02.

4. **Medium, LV-04 — QEMU share paths are passed as unescaped option values.** `render_qemu_args` interpolates each host path into `local,id=...,path={path},security_model=passthrough` (`vm/linux.rs:352-365`). A user's stage path may contain a comma; QEMU parses commas as option separators. Its [invocation reference](https://www.qemu.org/docs/master/system/invocation.html) requires doubling commas in arbitrary option string values. Trigger: a home/stage path with a comma, or a crafted path segment resembling another `-fsdev` suboption. The share can point somewhere other than the validated path, fail to start, or alter parsed options; separate `Command` arguments do not prevent suboption parsing. **Fix:** escape QEMU option values or use a structured configuration transport, reject lossy non-UTF-8 paths, and test comma-bearing stage paths against QEMU's parser.

5. **Medium, LV-05 — `O_PATH` handles do not lock QEMU's pathname mappings.** The host rewalks and opens stage/mount objects with `O_PATH` (`vm/linux.rs:271-278,685-710`), but `-fsdev` still supplies path strings (`:352-365`). A same-uid actor able to rename/replace a stage directory after the last identity check can make QEMU resolve a different tree. [Linux `rename(2)`](https://man7.org/linux/man-pages/man2/rename.2.html) explicitly leaves already open descriptors unaffected, which is why the pinned inode and later pathname can diverge. The code's comment that the handles block replacement is therefore unsupported. **Fix:** make the mapped namespace nonreplaceable by the attacker through ownership/permissions or pass stable fd-backed paths with QEMU semantics verified; test a swap between validation and share open. Treat the control/result and package grant boundaries as part of that proof.

6. **Medium, LV-06 — root preparation's QEMU queries are not bounded by their stated deadline.** `prepare.rs:521-571` waits for a QEMU help process before draining piped stdout. A verbose `-device help`/`-M help` response can fill the pipe and block the child, leading to timeout; after a parent exit, `read_to_end` has no deadline if a descendant retains stdout. Timeout and wait-error branches ignore kill/wait errors. These are trusted root-owned QEMU queries, so this is primarily preparation availability and cleanup uncertainty, not an untrusted-code execution claim. **Fix:** concurrently and cap-drain stdout during the wait, bound the entire process tree and reader completion, and surface uncertain cleanup. Test a dual-process/pipe-pressure fixture.

7. **Medium, LV-07 — non-merged system tool paths and compressed module names are not handled consistently.** Preparation accepts BusyBox, setpriv and kmod from `/bin` (`prepare.rs:36-39,182-190`), but generated `/init` hardcodes `/usr/bin/busybox`, `/usr/bin/setpriv` and `/usr/bin/kmod` (`:868-883,907`); a host using only the accepted `/bin` locations prepares an image that cannot execute its init/tool steps. Module parsing also strips only `.ko` from `modules.dep` names (`:587-626`), so `.ko.xz` or `.ko.zst` entries do not match required names such as `virtio_mmio`. **Fix:** render the actual selected guest binary paths, normalize supported module compression suffixes and dependency closure, and exercise those layouts in fixtures and a real boot.

## Source structure and authority limits

The host selects the Linux backend only for explicit `backend=vm`; `auto` remains outside it (`sandbox/mod.rs:55-59`). `classify_kvm` maps a missing `/dev/kvm` to `Absent` and therefore to a reasoned platform fallback; permission denial, missing preparation, stale hashes and runtime errors remain selected and unavailable (`vm/linux.rs:55-67,108-159`). This is a defensible source distinction, though a missing KVM device with CPU virtualization flags is an OS-feature absence inference, not a tested hardware proof. `vm status` is read-only and `prepare`/`remove` reject non-root (`prepare.rs:101-123`); protected state records kernel, initramfs and QEMU hashes and verifies them in preflight (`:264-284,343-383`). Root idempotence and real prepare/remove remain untested.

The initramfs builder parses ELF dependencies rather than calling `ldd` (`prepare.rs:674-822`), copies selected files and a bounded `/etc` allowlist (`:824-862`), and adds modules or built-in support (`:585-661`). QEMU args use explicit virtio MMIO 9p/network devices and enforce the eight-transport budget (`vm/linux.rs:260-264,321-371`), addressing CR-025 in shape, subject to LV-04 and boot verification. The guest job namespace `/mnt/fail2commit-vm/jobs/<id>` is outside Bubblewrap's `/f2c` control mount; request and result use separate roots (`prepare.rs:896-908`, `vm_guest.rs:205-240`), addressing CR-027 in layout, subject to LV-01. The host's writable share is work plus the separate result exchange; system/input shares and control are marked read-only (`vm/linux.rs:228-259`). The package's actual inner grants, mount flags and network/bait effects need boot tests.

The host reads a bounded no-follow outcome and checks its job ID (`vm/linux.rs:493-522`; `hardened/protocol.rs:221-266`); the decoder also rejects guest `exported` claims (`protocol.rs:395-427`). On the successful path it waits for clean QEMU exit before returning that outcome (`vm/linux.rs:291-316`), after which the common `sandbox::run_job` alone decides export on `Exited(0)` (`sandbox/mod.rs:78-91`). The ID is correlation, not authentication against a peer able to write the result share; the trust boundary rests on control/result isolation and VM exit. Timeout sends `SIGKILL` to QEMU's process group and checks group absence (`vm/linux.rs:543-569`), but no real process-tree, timeout, killed-VM or export sequencing test ran. LV-03 is an explicit post-spawn cleanup hole.
