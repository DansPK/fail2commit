## New findings

1. **Medium, VM-R3-01 — query descendants can start before job ownership.** `run_bounded_control` calls ordinary `Command::spawn()` at `vm/windows.rs:752-754` and only then calls `VmControlTree::assign(child.id())` at `:755`. The FFI creates/configures the job and opens/assigns the already running process afterward (`windows/ffi.rs:687-719`). A query that starts a descendant, or exits, in that interval can leave the descendant outside the new job. On assignment failure the caller kills/reaps only the root (`vm/windows.rs:757-770`) and explicitly cannot verify descendants. `KILL_ON_JOB_CLOSE`, `ActiveProcesses == 0`, and `TerminateJobObject` therefore prove only the members that entered this job, not the whole query tree. The supplied descendant fixture (`:1020-1060`) exercises a common scheduling path, not this race. **Fix:** create the query root suspended, assign and verify its job membership, then resume it; keep fail-closed cleanup for any assign/resume error and test forced assignment delay with a fast-spawning child.

2. **Medium, VM-R3-02 — pipe readers can run past the deadline and block `join`.** `read_capped_pipe` checks `Instant::now() >= deadline` only when `PeekNamedPipe` reports zero available bytes (`vm/windows.rs:709-725`). A stream that remains readable can keep the loop running after the deadline. The caller handles a deadline/status failure, then joins both threads without a join bound (`:818-826`), including when `terminate_control_tree` fails. The success path also joins before checking `closed` (`:834-840`); an unowned pipe writer from VM-R3-01 can prolong it. Capped storage limits memory, not elapsed reading time. The reported dual-pipe and retained-descendant tests cover finite output, not continuous output plus failed termination. **Fix:** check the deadline at the top of every reader iteration, return a timed-out/open state, and ensure all error returns can complete without waiting indefinitely for a reader. Test a continuously writing descendant and injected tree-termination failure.

`terminate_control_tree` first calls `TerminateJobObject`, then waits up to two seconds for an empty job and reaps the root (`vm/windows.rs:851-865`). Errors are surfaced as uncertainty, not treated as success. If `tree.terminate()` fails, its early `?` leaves explicit root cleanup to handle-drop behavior for assigned members; it cannot recover an unassigned descendant from VM-R3-01. The job handle is held through process/pipe observation and dropped on return. `read_capped_pipe` peeks before each bounded-size read, so the original idle-pipe blocking pattern is addressed in source, subject to the elapsed-time gap above.
