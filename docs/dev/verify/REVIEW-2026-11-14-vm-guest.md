# VM guest launcher source review — 2026-11-14

**Pin:** `0be8e9ca7b32ee88e2e344dae8d3344819702cd2` (`DansPK/f2c-014-vm`), against its parent. Reviewed SPEC-019 and CR-025 (`a91758d798b62efe6552f811665619676b87718d`). **Verdict:** guest-path source is **not ready for host-backend integration**. The unchanged Windows backend rejects the specified guest layout. VM host backends, QEMU/WSB lifecycle, outcome consumption, and runtime containment are absent or unverified; this is not FR-029 acceptance.

## Findings

1. **High, VG-01 — Windows guest jobs cannot pass the unchanged backend's stage validation.** `vm_guest.rs:67-88` fixes `work_dir` at `C:\f2c\work` and read-only mounts at `C:\f2c\in`/`bin`; `vm_guest.rs:39` calls `platform_backend()`. The Windows backend chooses `<trusted cache>/sandbox-stage` as its validation root (`windows.rs:495-502,1570-1599`) and requires `work_dir` to be below a *child job stage* and every read-only input in that same stage (`windows.rs:1434-1492`). The fixed mapped folders cannot meet those predicates, so a valid SPEC-019 Windows guest request fails before the AppContainer launch. A relocation of `FAIL2COMMIT_HOME` alone does not resolve the disjoint read-only roots. **Fix:** provide an authenticated guest-specific stage root/layout to the existing backend, or stage the mapped inputs and work below one backend-valid job stage while preserving the specified host mapping and export behavior. Test the actual `vm_guest_launch` -> AppContainer path in WSB.

2. **Medium, VG-02 — assigned-mount validation compares path spelling, not resolved identity.** `protocol.rs:171-207` accepts any clean path lexically under a fixed mount; `vm_guest.rs:35-39` then passes it to backends that canonicalize it (`linux.rs:398-422,569-595`; `windows.rs:1434-1443`). A symlink/junction inside an assigned mount can resolve outside it. On Linux, for example, a read-only path under `/f2c/job` linking to an otherwise bindable guest path outside the assigned mounts can be accepted and bound; the validation has not established the claimed guest-mount boundary. **Fix:** validate opened/canonical identities of mount anchors and every staged path, reject links/reparse escapes, and bind or recheck the same identities at use; test link swaps and mount-root aliases. The inner backends' own restrictions reduce exposure but do not prove this envelope.

3. **Medium, VG-03 — metadata-before-open race defeats the claimed bounded regular-file transport.** `vm_guest.rs:17-30` checks `symlink_metadata(jobfile)`, then separately opens the path and performs a byte-limited `read_to_end`. A writer of the mapped job directory can exchange the checked file for a FIFO/special target or reparse target between those operations. On Linux a FIFO `open` can block without reaching the 1 MiB byte limit; the bytes may also come from a different file than the checked one. **Fix:** open once without following links/reparse points, inspect the opened handle's type and size, and apply a read deadline or require immutable handoff before launch. Add a replacement/special-file regression. The outer VM timeout is specified but is not implemented in this pin.

4. **Medium, VG-04 — Windows error paths leave the guest running without a completion record.** `vm_guest.rs:11-50` uses `?` for validation, backend, serialization and outcome publication; the `shutdown.exe` call at `:52-63` is reached only after successful publication. A malformed job, failed inner probe, failed backend, or output encoding failure yields no outcome and no requested shutdown. The future host timeout can eventually kill WSB, but normal prompt failure/shutdown is not met. **Fix:** run a shutdown finalizer on every Windows guest exit path and publish a bounded failure record where the protocol permits; preserve failure exit status. Test malformed request and inner-backend error paths in WSB.

## Source disposition and integration gates

- **Supported by source:** `vm_guest.rs:27-32` caps bytes read at 1 MiB, and `protocol.rs:159-165` rejects an oversized or malformed JSON job. `protocol.rs:171-207` rejects `..`, `.`, relative paths, nonfixed `work_dir`, and `export_to`; its unit at `:422-444` covers those lexical cases only. `vm_guest.rs:39` selects the unchanged platform backend. `vm_guest.rs:43-50` writes a temporary outcome, syncs its file, then renames it on the success path. No guest export occurs because `export_to` is rejected.
- **Unproven or absent:** The hidden `--vm-guest` flag is directly dispatched from `main.rs:170-220` through `cmd/sandbox.rs:131-143`, without a guest-context/capability check; hiding a flag does not authenticate a VM. This snapshot has no host package-policy or VM-launch path that invokes it, so a host-policy bypass is **not demonstrated**, but host integration must establish that an untrusted caller cannot use the flag as a substitute for the guarded package path. The shared writable work mount also lets a job write `outcome.json`; a future host reader must require VM termination, validate bounded schema/status, reject stale or forged results, and bind the result to its job. None of those host checks exist here. File `sync_all` does not establish directory durability after rename. CR-025's MMIO device checks, QEMU preparation/probe and cleanup, WSB/QEMU runtime effects, and host export gating are pending because the host backends are not in this pin.
- **Checks:** `git diff --check 0be8e9ca^ 0be8e9ca` exited **0**; source inspection of the five changed files, SPEC-019, CR-025, and the relevant unchanged backend validators. The worker-reported `fmt`, default/diagnostic `check`, and one path-validation test were not rerun; they do not exercise the Windows guest layout or hostile file/path replacement. No privileged host or VM test was run.
