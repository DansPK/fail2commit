# FR-027 WFP proxy permit review (2026-11-14)

**Pinned implementation:** `22648966113918758a1aa898399d0c05023b1964`, including `37be13d73a9af7a8c568f6073ed99c777a1ed4fb`; delta from `e0d9e3d2c2f8aa34c205636e672a31d7e78916e9`. **Prior review:** `75fcc6724bf3ea671ed8c2a0763211d516ad5432`. **Verdict:** PX-01 is source-fixed and most of PX-02 is bounded, but the WFP permit does not encode the intended endpoint on little-endian Windows, exemption rollback can remove an entry it did not add, and proxy cancellation can still be delayed by a write under its state lock. Internet remains refused before service launch; these are pre-activation findings, not evidence that package traffic can currently use the route.

## Prior findings

- **PX-01 — source-fixed for the reported resolver race; runtime pending.** `SocketRegistry` serializes connect, registration, writes and cancellation through one `closed` state (`windows_proxy.rs:213-305`). A bait hit closes that state before publishing the trip (`:499-508`); a resolver returning afterward is checked before connect (`:510-549`), and later writes use `write_if_open` (`:564-590,898-900`). The paused-resolver fixture at `:1166-1221` checks zero connector calls after bait. See WP-03 for the remaining cancellation latency while a write holds the lock.
- **PX-02 — partially source-fixed.** A process-wide two-worker DNS pool bounds request-side waiting to two seconds and avoids joining blocked OS resolvers (`windows_proxy.rs:35-135`); request reads use a monotonic ten-second deadline (`:477-485,608-714`), and tunnel loops check idle and maximum-lifetime deadlines (`:858-900`). Registry closure prevents post-shutdown registration (`:213-233`). Slow-client and trickle fixtures are present (`:1223-1285`). A blocking `write_all` under the registry lock still defeats a strict cancellation/teardown bound (WP-03).
- **Authority parser — source-fixed for the earlier ambiguity.** The shared parser now requires strict UTF-8 request lines, one recognized HTTP/1.x version and a valid method; bracketed authorities must be valid IPv6 with no trailing text (`egress.rs:49-133`). Malformed authority assertions are at `:183-199`. Destination DNS answers are still checked as a whole before connecting to the selected `SocketAddr` (`windows_proxy.rs:528-561`).

## New findings

### WP-01 — High, pre-activation: WFP permit encodes the wrong IPv4 address and port

`windows_wfp.rs:150-181` puts `u32::from_ne_bytes([127,0,0,1])` into `FWP_V4_ADDR_AND_MASK.addr` and `port.to_be()` into a `FWP_UINT16` remote-port condition. Microsoft specifies [host order for `FWP_V4_ADDR_AND_MASK`](https://learn.microsoft.com/en-us/windows/win32/api/fwptypes/ns-fwptypes-fwp_v4_addr_and_mask) and [host order for `FWP_UINT16` ports](https://learn.microsoft.com/en-us/windows/win32/fwp/filtering-condition-identifiers-). On little-endian Windows the address expression is `0x0100007F` rather than `0x7F000001` (127.0.0.1), and an example port 32123 is swapped to 31613. The readback repeats the same mistaken expressions (`windows_wfp.rs:324-339`), so it can approve the wrong filter. If Internet launch were enabled, the higher-weight permit could allow the package to an unintended address/port while refusing the actual proxy endpoint, subject to WFP's unverified traffic behavior. **Fix:** encode the IPv4 address as a host-order numeric value (for example `u32::from_be_bytes([127,0,0,1])`), use the unchanged host-order `port`, read back those independently derived values, and run positive loopback plus negative swapped-address/port traffic probes in the disposable VM.

### WP-02 — Medium, pre-activation: rollback may delete a pre-existing loopback exemption

`PackageGuard::install` sets `exemption_added = true` *before* `add_loopback_exemption` (`windows_wfp.rs:58-68`). That add call returns an error without mutation when the exact SID is already exempt (`windows/ffi.rs:1572-1584`). The setup error then calls `guard.close()` (`windows_wfp.rs:83-91`), which removes that SID whenever `exemption_added` is true (`:358-362`). Trigger: another administrator or process adds the fresh package SID between the launcher's no-exemption check (`windows.rs:575,2103-2110`) and the service add, or the list already contains it. The service removes an exemption it did not create, altering shared OS state. **Fix:** distinguish intent to add from a confirmed successful add; on ambiguous API failure, compare pre/post state and preserve ownership evidence rather than blindly deleting the SID. Exercise pre-existing-SID and failed-add fault cases in a disposable VM.

### WP-03 — Medium, pre-activation: blocking writes hold the cancellation lock

`write_if_open` keeps `SocketRegistry.state` locked for `stream.write_all(bytes)` (`windows_proxy.rs:267-279`), while bait cancellation and drop need that same lock (`:281-305,175-193`). `write_all` retries partial writes until the whole buffer is sent, and the 250 ms socket write timeout is per underlying operation, not a monotonic deadline ([Rust `Write::write_all`](https://doc.rust-lang.org/std/io/trait.Write.html#method.write_all); `windows_proxy.rs:30-31,559-560`). A slow-reading upstream or client can keep making small progress on a 16 KiB tunnel chunk (`:867-900`) while the bait worker is blocked trying to commit `closed`; the connection lifetime check is outside the write loop. Drop can wait similarly. **Fix:** do bounded nonblocking or deadline-aware writes without holding the state mutex across I/O, while retaining an atomic cancellation/registration rule; add a slow-reader fixture that trips bait during an in-progress write and asserts a bounded stop and zero subsequent bytes.

### WP-04 — Medium, pre-activation: whole-list loopback updates can erase concurrent entries

`add_loopback_exemption` and `remove_loopback_exemption` read the machine-wide list, rewrite the *entire* list, and verify only that expected entries are present afterward (`windows/ffi.rs:1572-1629`). Their mutex (`:1509`) protects only this process. If another process adds an unrelated exemption between this service's read and write, its entry is omitted from the submitted list and removed; the subset readback still succeeds. Microsoft makes preserving existing entries the caller's responsibility for [NetworkIsolationSetAppContainerConfig](https://learn.microsoft.com/en-us/windows/win32/api/netfw/nf-netfw-networkisolationsetappcontainerconfig). **Fix:** coordinate updates across processes or use an OS mechanism with per-SID atomic updates; at minimum detect any concurrent list change and refuse/restore without clobbering unrelated entries. Verify concurrent add/remove restoration in a disposable VM.

## Boundaries and checks

- The permit is structurally scoped to one package SID, IPv4 connect layer, TCP, address and port; it has weight `u64::MAX` versus deny `MAX-1` in the same universal sublayer (`windows_wfp.rs:96-227`). Readback verifies layer, sublayer, action, weight and four conditions (`:272-353`), but cannot establish traffic effects, and WP-01 means the endpoint values are wrong. Six deny layers remain installed for both address families. The exemption intent journal is created before the add, parsed with owner/type/size checks on restart, and used to remove only its recorded SID (`:449-527`); failure leaves the service locked (`service.rs:1803-1809`). Journal creation checks for SYSTEM ownership without setting it (`windows_wfp.rs:463-477`); prior Win10 service-created objects defaulted to Administrators ownership, so this path needs an exact VM owner/readback probe before it can be assumed functional.
- The preparation request/ack binds network mode and proxy port to the existing launch/package identity (`service.rs:1187-1263,1329-1423`); the launcher binds the receipt to its bound port before resume (`windows.rs:533-549,701-720`). The SYSTEM service rejects Internet in `launch_windows_request` before preparation or package execution (`service.rs:3387-3397`), and `run_windows` also refuses it from STATUS (`:91-97`). No WFP traffic-effect probe exists. The stated proxy 9/service 26/egress 2/policy 1 test passes were reported by the worker and were not rerun; pure policy tests do not prove filter ordering, exemption effects, loopback permit or direct-route denial.
- **Exact checks:** clean worktree before branch creation; `git rev-parse` of `37be13d` and pinned `2264896`, `git log`, targeted `git diff`/`rg` and numbered source reads all exited `0`. A PowerShell byte-order calculation exited `0`: `[127,0,0,1]` as native little-endian is `0x0100007F` versus intended `0x7F000001`; 32123 swaps to 31613. Microsoft WFP and Rust standard-library documentation were checked for the relevant semantics. No cold broad build, VM or host privileged action, production edit, push or publish occurred.
