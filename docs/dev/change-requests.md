# Change requests

Material behavior decisions made during implementation. The project rule is to log each material behavior change here and carry on with independent work. Each entry names its trigger, the decision and the affected requirement. The requirement baseline in docs/dev/requirements is unchanged; these refine how it is met.

| ID | Date | Trigger | Decision | Affects |
|---|---|---|---|---|
| CR-001 | 2026-11-09 | Review W2-001: CPython `site` runs `.pth`/`sitecustomize.py` from installed wheels at every interpreter start, including fail2commit's own probe and verify runs. | fail2commit starts Python without `site` (`-S` with an explicit `sys.path`), so wheel startup code never runs inside the guard. A reviewed wheel that installs an import-bearing `*.pth`, `sitecustomize.py` or `usercustomize.py` gets an approval finding naming each file, because that code will run whenever the user next starts Python. Not a hard deny: common packages such as setuptools ship one. | FR-005, FR-008 |
| CR-002 | 2026-11-09 | Review W2-002: an interrupted or cancelled pip apply was rolled forward silently by the next unrelated install, replaying the earlier approval. | Never roll forward automatically. While a journal exists, guarded pip installs for that interpreter stop with a clear message. `fail2commit pip recover` shows the unfinished plan and either completes it after a fresh approval, or discards the journal. A cancel before apply starts changes nothing; a cancel mid-apply stops at the next wheel boundary and leaves a journal. | FR-005, FR-002 |
| CR-003 | 2026-11-09 | Review W2-008: known-malware findings were approvable with one click. | Known malware (OSV `MAL-` ids and OpenSSF malicious-packages records) is a hard `Deny` for that package. Ordinary advisories and incomplete scans stay one-time approvable as SPEC-006 states. | FR-006 |
| CR-005 | 2026-11-09 | pip re-review RP-003/RP-004: a reviewed wheel could replace pip itself or write `pyvenv.cfg`/`Lib`/`bin`/`Scripts` through the data scheme, so the guard's next interpreter start ran its code. | The guard runs pip only from a private, hash-checked snapshot taken before anything is installed. Wheels that write into `pip/`, interpreter startup paths or venv executables are a hard `Deny`. Upgrading pip itself through the guard is unsupported. | FR-005, FR-008 |
| CR-006 | 2026-11-09 | T-007b review S7B-009 and source review in docs/sandbox-windows.md §1: every usable `sandboxrs-windows 0.1.1` AppContainer path applies broad system-directory ACL grants, `FILE_ALL_ACCESS` on writable roots, and an unsandboxed, `%TEMP%`-anchored probe. | SPEC-007's Windows backend is implemented directly on `windows-sys` (AppContainer, Job Objects, handle lists, handle-based ACL grants). The unused `sandboxrs-windows` pin is removed. LPAC remains unclaimed until verified. | FR-007 |
| CR-007 | 2026-11-09 | T-007b fix: grants must anchor on a fail2commit-owned root. | Every sandbox job stage (npm, pip, `fail2commit run`) is a direct child of `<cache_dir>/sandbox-stage`. | FR-007, FR-004 |
| CR-008 | 2026-11-09 | npm re-review 2 (RN2-001..004): our tar/gzip parsing disagreed with npm's extractor (concatenated gzip members, a single zero block, header-type confusion, pacote's `.gitignore` rename), so the reviewed manifest and scripts could differ from what npm installs. | Review the tree npm itself extracts, not a separate parse. The staged install runs `npm ci --offline --ignore-scripts` (no package code), and the manifests, lifecycle scripts and referenced files are then read from the extracted staging tree on disk. Archive pre-checks remain defense in depth only. The commit/apply step uses that same reviewed tree. | FR-004, FR-006 |
| CR-010 | 2026-11-09 | Relay review ER-001/ER-002: the CR-009 loopback relay token was inherited by chained hooks and other git children, the relay was reusable, forged password-required requests could harvest the typed password, and any stdio approver honored the relay variable. | Supersedes the CR-009 transport: the relay host (the trusted parent `fail2commit git push`) runs the full approval including password verification and returns only an HMAC-authenticated decision bound to request id, nonce and digest. The relay is single-use with deadlines. The hook strips the relay variable before chaining hooks. Only the hook entry point is a relay client. | FR-001, FR-002 |
| CR-011 | 2026-11-09 | Relay re-review RR-004: git's own children during a push (`receive-pack`, `core.sshCommand`, credential helpers) inherit the relay token. | Accepted residual risk: anything git runs during a push is code executing as the user, which can already push without fail2commit. Protected refs rely on the remote receive policy (SPEC-003), per docs/ARCHITECTURE.md trust boundaries. Mitigations kept: the token is per push and single-use, the listener stays bound until the push ends (no port takeover), the host binds the request to its own push and clamps expiry, and only decisions cross the relay (CR-010). Documented in docs/approval.md. | FR-001, FR-002, FR-003 |
| CR-012 | 2026-11-09 | Final gate: the real Linux native-build test compiles `build/addon` and then runs it, and the "path absent at review is a hard deny" rule from the RN3 follow-up blocked it, contradicting FR-007's "native build succeeds". | A lifecycle command path with no candidate on disk at review is an `IncompleteScan` `Approve` finding that names it (built or created at runtime, not inspected), rather than a `Deny`. Candidates that could shadow a reviewed file still must stay absent, and a re-check before each script fails closed if one appears. Hard denials remain for force-push scripts, integrity failures and uninspectable referenced content. Pattern checks are evidence; the sandbox is the boundary (SPEC-006). | FR-004, FR-006, FR-007 |
| CR-013 | 2026-11-09 | Owner's PC test: plain `npm install` was not guarded. Windows builds a process PATH as machine PATH then user PATH, so the per-user shims from `fail2commit setup` never win against a Node.js (or Python) installed for all users, such as `C:\Program Files\nodejs\npm.cmd`. | Owner's choice: an optional, administrator-approved machine mode. `fail2commit machine-shims install` (run elevated by the installer's "Guard machine-wide npm and pip" section, default on, skipped in silent installs) copies the CLI as `npm.exe`, `pip.exe`, `pip3.exe` and `fail2commit.exe` into `<ProgramFilesDir>\fail2commit\shims` (admin-only; location read from HKLM, not the environment), puts that directory first on the machine PATH, and keeps the undo record there. Never a user-writable directory on the machine PATH. Uninstall removes only that entry and the files. `fail2commit status` now reports what bare `npm` and `pip` resolve to and warns when it is not a guard. PATH edits broadcast `WM_SETTINGCHANGE` so new terminals see them without signing out. Not covered: programs that run `npm.cmd` or a Node/Python path explicitly. | FR-004, FR-005, FR-009 |
| CR-014 | 2026-11-09 | Owner-requested Windows flow: `npm install esbuild` hung 15 minutes in the AppContainer. libuv creates child stdio pipes in the global named-pipe namespace, which an AppContainer may not do, and retries forever. | Sandboxed npm lifecycle scripts on Windows get a preload (`NODE_OPTIONS=--require f2c-node-preload.js`) that routes piped child stdio through files in the job's temp directory (`F2C_IO_DIR`). No isolation is relaxed: the AppContainer, ACLs, network denial and job limits are unchanged, and the preload only runs inside the job. Writes to an async child's stdin, `fork()` IPC and non-Node named-pipe users remain unsupported and fail closed with a clear timeout message. | FR-004, FR-007 |
| CR-015 | 2026-11-09 | Owner-requested Linux flow on a real Debian 13 VM: inside an activated virtualenv, plain `pip install` bypassed fail2commit because `venv/bin` comes first on PATH (nvm/fnm do the same for npm). | `fail2commit setup` adds a recorded, marked block of shell functions (`pip`, `pip3`, `npm` calling the guard) to `~/.bashrc`, an existing `~/.zshrc`, an existing Git Bash `~/.bashrc` and the PowerShell 5.1/7 profiles. Functions win over PATH. In a venv the guard still targets the venv's Python (the one next to the first real `pip`). `uninstall-integrations` removes exactly the block. Tests redirect it with `FAIL2COMMIT_PATH_TARGET`. cmd.exe has no functions; `fail2commit pip` / `fail2commit npm` remain the explicit forms there. | FR-004, FR-005 |
| CR-016 | 2026-11-10 | Owner request: support Arch-based Linux. FR-011 supplied only a Debian/Ubuntu `.deb` and a source archive. | Add `packaging/arch/PKGBUILD`, which builds offline (`cargo --frozen`) from the vendored release source tarball, runs the core unit tests in `check()`, and installs only `/usr/bin/fail2commit`, licenses and docs (no install scriptlet, no home-directory edits). Depends on `git` and `bubblewrap`; Node/npm/Python are optional. `scripts/release/build-arch.sh` builds it with `makepkg` in a clean `archlinux` container as an unprivileged user, and `scripts/release/verify-arch.sh` checks install, status and removal there. The package is a release-built artifact for Arch, Manjaro, EndeavourOS and other pacman-based distributions on x86_64; it is not published to the AUR. | FR-011 |
| CR-017 | 2026-11-10 | Owner request: when a user runs `npm install`, check for injected malicious code and warn before the install continues. The script scan (FR-006) only looked for Git force pushes in lifecycle scripts, and package code that runs on `require()` was never read, so the attack simulation's payloads were installed with no code warning. | Every package in an npm install plan is scanned as text, never executed (`scan/code.rs`). Seven rules: hidden code (decoded string executed, Base64 blobs rescanned), credential harvest (two or more credential stores in one file), environment harvest, download-and-run, data-drop addresses, persistence and CI backdoors. Each hit is a new `suspicious_code` finding with action `approve`, which says whether the code runs at install (sandboxed) or when the project loads the package (not sandboxed). Known malware stays the only hard deny (CR-003). Install-time text gets every rule; runtime code only gets the rules for actions inside exec calls or file writes, and a package's own test files are skipped, because help text and helper scripts mention downloads and shell files without running them. Bounded: 16 MiB per file, 64 MiB per package, 8 findings per package. Advisory findings now lead with severity and the fixed-in version. | FR-006, FR-004, FR-002 |
| CR-018 | 2026-11-10 | Owner request (0.1.3, P-108): verify package signatures. The npm guard checked the lockfile integrity hash only, so a tampered registry or mirror that also served a matching lockfile hash, or a hijacked publish, was not detected. | Before install, every npm artifact in the plan is checked against the registry's ECDSA signature (`dist.signatures`, keys from `<registry>/-/npm/v1/keys`, cached for `signatures.keys_ttl_secs`). A missing, unverifiable or invalid signature is a `signature_invalid` deny. When an earlier version of the same package had Sigstore provenance and this one has none, a `provenance_missing` warning needs approval. `signatures.verify = false` turns the check off and is reported by `status`. | FR-004, FR-006 |
| CR-019 | 2026-11-10 | Owner request (0.1.3, P-109): harden the advisory connection. `osv_url` accepted plain `http://` to any host, and cached advisory entries were trusted as written. | `osv_url` must be `https://`, except `http://` to a loopback address (tests). Cache entries carry an integrity tag keyed by a per-user secret in the private data directory; an entry whose tag does not verify is discarded and refetched, never used. | FR-006, NFR-012 |
| CR-022 | 2026-11-11 | Owner decision for 0.1.4: install scripts must be able to pull dependencies and prebuilt binaries, so "no network" breaks real packages. | Sandboxed lifecycle scripts may reach public internet addresses only (FR-023). Loopback, private, link-local, metadata, multicast and local IPv6 ranges, names resolving to them, listening sockets, local sockets and named pipes stay refused. `sandbox.network = "none"` keeps the 0.1.3 behaviour. Exfiltration risk is reduced by the bait credentials (FR-024), the behaviour report (FR-026) and scanning script output (FR-028); the sandbox still grants no access to user secrets. The frozen `isolation` contract gains a network field. | FR-007, FR-023 |
| CR-021 | 2026-11-11 | Linux uninstall test: removing the package before `uninstall-integrations` made every `git push` fail ("fail2commit: not found") and the shell `npm`/`pip` functions exit 127; setup also set `$HOME` to 0700, rewrote shell startup files as 0600 and replaced a symlinked `~/.bashrc` with a copy. | The pre-push hook and the POSIX shell functions check that the fail2commit binary still exists; if it does not, the hook prints that the push was not checked and lets Git continue, and the functions run the real command. | CR-004 | 2026-11-09 | Review W2-003/W2-004: referenced script files that could not be decoded, ran past the inspection prefix, had no recognized extension, or were dropped by archive caps produced a clean result. | Any referenced script content that is not fully inspected yields an `IncompleteScan` `Deny` for that package's scripts. | CR-009 | 2026-11-09 | E2E: a forced push driven through `fail2commit api` could not be approved.
