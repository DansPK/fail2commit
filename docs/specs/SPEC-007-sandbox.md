# SPEC-007 — Automatic sandbox execution

FR-007 · TC-007 · Owner paths: Windows and Linux sandbox modules, run command implementation, fixtures.

Run a backend capability check before any dependency script starts. On Windows, integrate sandboxrs-windows with AppContainer, not its newer VM/API path. Review source and pin an exact release/revision. Verify no network or loopback capability/exemption, restrictive staging ACLs, no inherited credential handles, no permission on approval IPC, child process confinement and Job Object limits. Confirm whether the selected dependency configuration supports LPAC; no LPAC claim until verified. Add a narrowly scoped upstream fix or pinned patch if mandatory controls are missing. On Linux, use Bubblewrap with a clean environment, isolated network/PID/IPC namespaces and explicit mounts. Probe the actual availability of user namespaces and use cgroup controls where supported. Never mount host home, real checkout, secrets, credential sockets or control sockets.

Stage a minimal approved toolchain and reviewed package inputs read-only. Give each operation a disposable writable work directory. Clear environment except allowed tool settings. Run allowed scripts automatically when required and enabled. No sandbox starts for a script-free install. Enforce timeout, process cleanup, memory/process bounds where supported and bounded logs. Preserve expected package-manager lifecycle semantics. Treat output as untrusted. Wait for children to stop, reject unexpected paths, links, reparse points and oversized output, and copy only allowed artifacts. Never export on failure/cancel. Test explicit fail2commit run with staged project input and declared export paths. If isolation is unavailable or cannot enforce policy, stop before code executes. Runtime tracing is optional evidence only and is never used to decide whether network denial works.
